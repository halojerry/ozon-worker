# 常见越界行为与故障模式（Gotchas）

> Agent 操作 Skill 时的硬性纪律对照表。每次操作前自查，避免管线混乱。
> 故障模式采用 ❌/✅ 对比：❌ 错误做法 → 后果，✅ 正确做法。

## 行为越界（Anti-patterns）

| ❌ 错误行为 | 后果 | ✅ 正确做法 |
|---------|------|---------|
| 自己写 Python 代码调 API | 逻辑不完整、缺错误处理 | 用 `cli.py` 命令 |
| 自己探索项目目录结构 | 浪费时间、可能改错文件 | 看 SKILL.md 及 references |
| 给 Ozon URL 还去算蓝海评分 | 逻辑混乱 | 有 URL 直接处理 |
| 给 1688 URL 还去 Ozon 搜索 | 多余操作 | 有 URL 直接处理 |
| 替用户决定"这个利润太低不上了" | 用户失去控制权 | 展示数据让用户决定 |
| 在用户没说"提交"时就提交 Worker | 用户没确认就上架 | 等用户明确说"提交" |
| 对话长了就忘记意图路由规则 | 管线混乱 | 每次操作前重读 SKILL.md §1 |
| 把蓝海逻辑混入跟卖流程 | 数据错误 | 蓝海只在管线 C |

## 故障模式（命令执行时的坑）

| ❌ 场景 | 后果 | ✅ 正确做法 |
|--------|------|-----------|
| 搜索页/类目页 URL 走 follow（跟卖单商品） | 解析失败、浪费时间 | 走 discover `--url`（管线 C） |
| 读 `cli.py` 源码研究命令用法 | 浪费上下文（Cython 编译不可读） | 先 `--help` 看用法 |
| 图搜 `no_relevant_match=true` 仍组装信封提交 | 空壳上架被 Worker 拦截 | 直接拦截，询问换图/换货源 |
| 收到 `DUPLICATE_SUBMIT` 反复重提同一商品 | 永远 409，浪费调用 | `query <task_id>` 查既有任务 |
| rejected/failed 后直接重跑原命令 | 若原商品 ID 不变仍可（终态不占去重），但重跑整流程浪费生图额度 | 优先走 `/resubmit_task` 重提（复用原载荷 + 重生成图片） |
| 多店铺场景省略 `--store` 用默认店铺 | 用错店铺凭证/定价 | 用户提到具体店铺必须显式传 `--store` |
| 自动化/管道模式遇 `input()` 确认 | EOFError 崩溃 | 命令已 EOF 安全（按自动规则/取消），勿在非交互环境依赖人工确认 |

## 核心纪律（三句话）

1. **只用 SKILL.md 中的命令**，不自己写 Python 代码、不用 requests/urllib 抓取
2. **提交/上架前必须等用户明确确认**（用户给了明确 URL 的 graph/follow 除外）
3. **每次操作前重新判断用户意图**，不因上下文惯性选择管线
