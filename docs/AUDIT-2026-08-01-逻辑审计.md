## 一、P0 — 必须先修（6 个）

### P0-1. CDP 图搜 awaitPromise 缺失 → 首选图搜恒失败，全靠 API 兜底（本末倒置）
- **证据**：`skill/scripts/lib/ozon_image_search.py:46-122` `_extract_results_from_tab` 的 JS 用**裸顶层 await**，但 `search_by_image_cdp:291` 调 `tab.evaluate(js, timeout=15)` 未传 `await_promise=True`（`cdp_client.py:138-179` 默认 False）→ 两种 Chrome 行为下结果都为空：SyntaxError 或 Promise 无 value。
- **对比**：项目内其它 3 处 async 求值全部正确传了 `await_promise=True`（`ozon_widget.py:282/291`、`ozon_scraper.py:519`），唯独此处漏掉。
- **后果**：`follow_sell_cloud` 3a-1（`cloud_probe.py:2404-2406`）和 `ozon_discovery` 图搜策略**永远拿不到结果**——每次白烧 30-60s + 2 个 tab，然后才轮到 AK API 兜底出结果；且 `:320` 无条件 `cache_set(ttl=21600)` 把空结果写 6h 缓存，连兜底的 CDP 前置尝试都被短路。
- **修复**：JS 包成 async IIFE `(async () => {...})()` + `tab.evaluate(js, await_promise=True, timeout=15)`；空结果不写缓存（参照 `ozon_widget.fetch_product_info:302-303` 降级不缓存模式）。
- **改动量**：~5 行。全项目性价比最高的一行修复。

### P0-2. 跟卖属性链路全断：payload 属性为空 + 全类目垃圾兜底属性（数据传递）
- **证据**：`follow_sell_import_node.py:184-190` 输出 `final_attributes` 键为 `id`（Ozon 格式），但 `prepare_ozon_upload_node.py:1131` 只读 `attr.get("attribute_id")` → 跟卖属性**全部**被判缺失跳过（1136-1138）。
- 中间还隔一层：`assemble_ozon_product_node.py:150-152` `_assemble_follow_sell` 把**字典值 ID**（`NO_BRAND_DICT_ID`=126745801）当**属性 ID** 写入（应为 85/5076）。
- **后果**：跟卖产品最终 payload 只剩 prepare 硬编码的 9048/8962/4958，外加 `_FALLBACK_FREE_TEXT_ATTRS`（`prepare_ozon_upload_node.py:1375-1402`）按食品/玩具设计的 7578 保质期 365 天、8050 成分"полимерные материалы"、9782 危险品等级**对所有类目一律追加**。
- **修复**：`_assemble_follow_sell` 直接消费 `follow_sell_import_node` 的 `final_attributes`（统一 `attribute_id` 键）；删 126745801 假属性；fallback 属性仅当该类目 schema 中存在该属性时才追加。

### P0-3. assemble 输出 4 个字段不在 GlobalState schema，被 Pydantic 静默丢弃（数据传递）
- **证据**：`assemble_ozon_product_node.py:915-927` 返回 `dictionary_values`、`learned_attributes`、`match_confidence`、`name`，`state.py:15-127` 均无这些字段（extra=ignore 静默丢弃）。
- **后果**：
  - `dictionary_values` 永远为空 → `prepare_ozon_upload_node.py:675-681` 字典补充、`:143-193` `_get_color_from_dictionary` 动态字典选色（2026-07-18 特性）**从未生效**，一直靠静态表兜底；
  - `match_confidence` 永远默认值 → `graph.py:180-183` 类目置信度 <0.3 阻断分支是死代码。
- **修复**：`state.py` 补 `dictionary_values: Dict[str, List[dict]]`、`match_confidence: float`（必要时补 `learned_attributes`、`name`）。

### P0-4. 单SKU/跟卖/发现管线漏加 1688 国内运费（契约断裂 + 定价）
- **证据**：`cloud_probe.py:1376-1379` `if len(variants) > 1:` 守卫 → `_collapse_variants_to_single` 内部已实现的 `len==1` 加运费分支（:663-669）**永远不可达**。
- **后果**：① 1688 商品本身只有 1 个 SKU → 不折叠 → `purchase_cost` 不含运费；② **跟卖路径**和**发现路径**强制 `max_skus=1`（`cloud_probe.py:2482-2487`、`1556-1561`）→ 这两条管线 **100% 漏加运费**（¥5-20），定价整体偏低、利润预估虚高，违反 CONTRACT.md §8。
- **修复**：无条件调用 `variants, cost_cny = _collapse_variants_to_single(variants, cost_cny, shipping)`（函数本身已兼容 0/1/N 变体）。

### P0-5. discover --auto-submit 凭证链路断裂（数据传递 + CLI 边界）
- **证据**：`cli.py:757-761` `from scripts.lib.config_store import load_store_config` — **该函数在整个代码库不存在** → 用户确认提交时 ImportError 崩溃。
- `build_envelope_from_discovery`（`cloud_probe.py:1556-1583`）拿到的完整 GraphInput 里**已包含解析好的凭证**（:1521-1526），但重新封装时全部丢弃，改用 `{"client_id": "", "api_key": ""}` → 提交空 Ozon 凭证，Worker 端 Ozon API 全失败。
- **修复**：`build_envelope_from_discovery` 透传 `result["ozon_client_id"]/["ozon_api_key"]/["token"]`；`cmd_discover` 删 `load_store_config` 引用，改用 `get_store()`。

### P0-6. 跟卖竞品价字段链路双重断裂 → "保持竞品价"定价是死代码（数据传递 + 定价）
- **证据**（两个独立断裂点）：
  1. skill 从不发送 Ozon 竞品价：`follow_sell_cloud` 只覆盖 images/title/ozon_category（`cloud_probe.py:2502-2510`），`draft["price"]` 仍是 1688 采购成本（:1441-1443）；Ozon 爬虫明明抓到了竞品价（`ozon_scraper.py:440` `result["price"]`）却被丢弃。worker 的 `follow_sell_import_node.py:159` 把 `draft.get("price")` 当竞品 Ozon 价——拿到的是 CNY 成本。
  2. `PricingInput` schema 缺 `competitor_price` 字段（`state.py:295-303`）→ `pricing_node` 里 `getattr(state, 'competitor_price', '')` 恒空（:224-227）。
- **后果**：`comp_price >= total_cost * 1.3` 分支（`pricing_node.py:228-239`）永不触发，跟卖永远公式重算，丢失竞品价跟随能力；字段值语义错位（CNY 成本被当 RUB 竞品价）。
- **修复**：skill 把爬到的 Ozon 竞品价写入信封 `draft["ozon_price"]`（discovery 已有 `candidate.ozon_price`）；worker `PricingInput` 补 `competitor_price` 字段，`follow_sell_import_node` 优先读 `draft["ozon_price"]` 而非 `draft["price"]`。

## 二、P1 — 重要（8 个）

### P1-1. quantity 数量变体拆分直接用 1688 采购价当 Ozon 售价（南辕北辙）

- **修复**：quantity 分支同样从 `pricing_info["variant_prices"]` 按索引取价。

### P1-2. assemble 部分失败分支不阻断，昂贵生图全部白跑（本末倒置）
- **证据**：`assemble_ozon_product_node.py:233-236`（标题空）与 `:594-597`（schema 获取失败）的 error_message 不含 `graph.py:177` 匹配的关键词，也不返回 match_confidence（P0-3 丢弃）→ 路由判"成功"→ 继续 scene_generation + 10 个生图节点（每次数百元）→ 直到 prepare 才失败，再进 retry loop 盲修。
- **修复**：assemble 所有失败分支统一返回可识别标记（error_message 前缀"类目匹配失败"或显式 `items` 为空），graph 路由加"items 为空 → END"。

### P1-3. main_image_gen 无参考图仍调生图 API，产出随机产品主图（本末倒置）

### P1-4. pricing 失败不阻断，产品按拍脑袋价 1000 上架（本末倒置）

### P1-5. retry loop 的 parse_error 忽略 validation_errors，本地预检失败首轮必为 UNKNOWN 盲修（数据传递）

### P1-6. probe_1688_page 每次先做 5-15s live 登录检查，无视已保存标记（本末倒置 + 舍近求远）

### P1-7. skill 侧 Ozon 真实佣金率查询是死代码（舍近求远 + 双重职责）

## 三、P2 — 建议（11 个）

### P2-1. 低密度场景三处处理互相矛盾（南辕北辙）
- `prepare_ozon_upload_node.py:844-847` 密度 <1.293 保持原值；`ozon_validate_node.py:146-166` 密度 <1.0 且 max_dim>500 **自动 ÷10**；`validation_retry_loop.py:1220-1229` repair_prepare 同样 ÷10。轻质大件（充气类）被错误缩小 10 倍上传。方向也存疑：cm 误标 mm 应放大而非缩小。
- **修复**：三处统一——validate/repair 不做自动除法，仅在尺寸超 Ozon 上限（>2000mm）时报错交 repair_dimensions 按密度重算。

### P2-2. pricing_node 真实佣金查询是死代码（舍近求远）
- `pricing_node.py:160-172` 用 `getattr(state, 'description_category_id', '')` 查佣金，但图拓扑是 `ingest → pricing → assemble`，pricing 执行时类目**必然为空** → 恒走 0.10 fallback；即便执行，`/v5/product/info/prices` 佣金在 `items[]` 内而非 `commissions`，解析也错。
- **修复**：删除该块，改为类目确定后（assemble 之后）查，或明确接受 10% 假设并在配置注明。

### P2-3. 小重量 ×1000 启发式与契约冲突（南辕北辙 / 单位往返）
- 契约保证 weight 克直传（CONTRACT.md:136，skill 侧 `_validate_and_fix_product_data` 密度校验 0.25-10 g/cm³ 保留轻小商品）。但 worker `pricing_node.py:111-118` 与 `prepare_ozon_upload_node.py:770-778` 各有一套 `<10g 且 max_dim>50mm → ×1000` 启发式，把真实轻小商品（5g 贴纸、100×70mm）放大成 5000g，两侧一致放大后互相无法纠错。与 `prepare:746-760`"skill 保证发送克"的注释自相矛盾。（注：AGENTS.md 把它记为有意启发式，但按契约它属于二次猜测，需决策。）
- **修复**：删除两处启发式；若保留，需 skill 侧按相同规则换算后再直传，保证只算一次。

### P2-4. 跨类目一致性校验双向失效（南辕北辙）
- `assemble_ozon_product_node.py:713-715` 取的是**中文**标题（组装阶段无翻译），`:1001-1038` RU 路径存在时中文 vs 俄语词必然无重叠 → **恒判定不一致** → 每次触发 pg_trgm 重匹配 + LLM 类目重排（白烧钱，可能把正确类目改成随机类目）；RU 路径缺失时 ZH_HANS 路径被 `len(word) >= 3` 过滤掉两字中文词 → `leaf_keywords` 空 → 恒通过，校验形同虚设。
- **修复**：一致性校验移到 prepare 完成俄语翻译之后；或组装时先翻译标题再校验。关联待办：.zcode 计划中的 jieba + LIKE 替代 pg_trgm。

### P2-5. 标签 23171 恒为 "#товар"（本末倒置）
- `assemble_ozon_product_node.py:1851` 在标题仍是中文时调 `_generate_hashtags`（:2008-2034），对非俄语标题 `re.findall(r'[а-яё]{3,}')` 无匹配 → 恒返回 `"#товар"`；`prepare_ozon_upload_node.py:1200-1216` 因含西里尔字母不再翻译。全量 1688 产品 hashtag 均为占位符。
- **修复**：hashtag 生成移到 prepare 标题翻译之后（用 title_ru），或 `_generate_hashtags` 增加中文标题俄语关键词兜底。

### P2-6. VARIANT_NOT_MERGED 靶向修复实际无效（数据传递）
- `validation_retry_loop.py:146` 映射到 repair_prepare，但 `repair_prepare_node`（:1159-1238）只修 9048 后缀与尺寸，**没有颜色去重**（去重逻辑只在 `prepare_ozon_upload_node.py:1750-1840`）；retry 不重跑 prepare → 同色变体必然 3 次循环失败后 END。

### P2-7. GlobalState 死字段 + 假计数器（数据传递）

### P2-8. ozon_validate 图片可达性用 HEAD，与已修复的 HEAD 拒绝矛盾（南辕北辙）

### P2-9. discover 每个产品新开 CDP 连接 + 2 tab（舍近求远）
- `ozon_discovery.py:470` `_search_1688_source` 调 `search_by_image_cdp` 时自建全新连接（:216），50 个产品 = 50 次连接、100 次 tab 开关。`ozon_widget.fetch_product_info` 已支持 `cdp=` 复用（:280-287）。

### P2-10. batch_test Ozon 分支：凭证覆盖死代码 + finally NameError 中断整批（南辕北辙 + 数据传递）
